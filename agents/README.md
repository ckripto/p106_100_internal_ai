# Протокол агентов

Coordinator использует JSON управления из `coordinator/prompt.md`. Executor и
Developer используют native `tools`/`tool_calls`, по одному вызову на ответ.
Transport проверяет finish_reason до разбора аргументов или выполнения инструмента.
Несовместимый, неполный или недоступный API даёт контролируемый failed.

## Tool runtime

`edit_file(path, old, new, expected_replacements, reason?)` атомарно выполняет
точную замену только при совпадении ожидаемого количества вхождений. `write_file`
собирает файл в памяти попытки: первая часть имеет offset 0, следующая использует
next_offset. Только final=true публикует файл через временный файл и `os.replace`;
оборванная часть не меняет существующий файл. `read_file` читает опубликованный или
staged файл ограниченными частями. `list_files` ограничивает число результатов.
`run_command` запускает Bash с
`pipefail`, непрерывно дренирует stdout/stderr, возвращает ограниченный префикс и
по тайм-ауту убивает process group.

Конкретные root, chunk/staging limits, сроки и step limits принадлежат настройкам
агента. Файловые инструменты не выходят за root; shell не является sandbox.
Три последовательные ошибки tool protocol завершают попытку. Snapshot передаёт
последний полный результат и компактную историю недавних действий. Повторное
чтение уже полученного path/offset отклоняется, а второй такой повтор завершает
попытку как цикл.

Executor использует `executor/runtime.py`: все его file/command tools идут через
BatchMode SSH на отдельный узел, а локальный fallback отсутствует. Developer
использует локальный `ToolState` общего runtime. Перед изменением Developer должен
полностью прочитать ближайший локальный `AGENTS.md`; runtime проверяет это до
`edit_file` и `write_file`.

Success требует хотя бы одного выполненного инструмента, отсутствия pending writes
и неисправленных ошибок. Ошибка снимается успешным повтором того же инструмента и
target. Это подтверждает фактическое исполнение, но не смысловую полноту задачи.

## Координация

Coordinator маршрутизирует пользовательскую работу Executor, а изменения системы
Developer. На информационный запрос без требуемых действий он отвечает решением
`answer`, не запуская исполнителя. Он хранит до восьми компактных результатов, не
передавая исходники и stdout. После тайм-аута требуется другая или более узкая подзадача. Три тайм-аута
либо три последовательных ошибки управляющего JSON завершают задачу с failed.
Предыдущие две пары пользовательская задача/итог доступны как контекст сессии.

Каждая отправленная подзадача, компактный ответ и наблюдаемый обмен агента с LLM
передаются callback `on_message`. Запись содержит направление, номер попытки или
шага, время, текст фактического сообщения и длительность ответа. Запросы к LLM не
содержат system prompt; ответы содержат разобранное решение/tool call либо тип
ошибки. Короткое поле `reason` объясняет цель действия без скрытой цепочки
рассуждений. Web-service сохраняет поток по мере выполнения. Максимум ожидания
ответа модели и одной попытки агента по умолчанию равен 300 секундам.

Настройки разделены по `coordinator/settings.py`, `executor/settings.py` и
`developer/settings.py`. Промпты находятся в соответствующих `prompt.md`.

Запуск: `venv/bin/python -m agents.coordinator`.
Тесты: `venv/bin/python -m pytest -q`.
